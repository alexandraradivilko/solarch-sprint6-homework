# Целевая архитектура: 12 месяцев

[Исходник схемы Mermaid](diagrams/target-data-architecture.mmd)

| Компонент | Роль в целевой архитектуре |
|---|---|
| Operational Systems: FU Core, CRM, Cards, Loans | Раздельные OLTP БД и профильные мастера по Task2. Core ведёт финансовый учёт по юридическим лицам; CRM ведёт обслуживание и согласия; Cards и Loans свои продукты. Остаточные системы RB подключены до переноса объектов |
| MDM Customer Hub | Золотые записи клиентов, соответствия ID, утверждённые продукты, тарифы и справочники; происхождение атрибутов и разбор конфликтов |
| Integration Layer | Синхронные API для обслуживания; адаптеры CDC/событий и batch для обмена. Проверяет схемы и права, маршрутизирует изменения |
| Kafka | Доставка событий источников и публикаций MDM в отдельных топиках, хранение позиций потребителей и возможность повторного чтения |
| PostgreSQL DWH | Слои staging → согласованное ядро → витрины; сверенные финансовые факты, остатки и регламентированная отчётность. Отдельный от OLTP экземпляр/кластер |
| Data Lakehouse | S3-совместимое объектное хранилище и таблицы Apache Iceberg для событий и большой истории. Spark выполняет batch и Structured Streaming; Trino даёт SQL-доступ к подготовленным таблицам |
| Iceberg REST Catalog | Технический каталог таблиц и их текущих метаданных для Spark/Trino. Отдельная функция от бизнес-каталога DataHub |
| BI | Сертифицированные дашборды из DWH; исследовательская аналитика через Trino. Прямых аналитических запросов к OLTP нет |
| Airflow | Расписание, зависимости, повторы и контроль batch-загрузок DWH, архивов и обслуживания таблиц Iceberg. Не обрабатывает поток событий вместо Spark |
| DataHub | Каталог наборов, владельцы, классификация, lineage, результаты проверок качества; получает метаданные загрузок и моделей |

Операционные изменения проходят через Integration Layer в Kafka. MDM получает клиентские данные и публикует эталоны; Integration Layer доставляет разрешённые проекции обратно в операционные системы. Обратные публикации реплик отсекаются по происхождению и версии. Профильные мастера финансовых данных сохраняются.

Для DWH Integration Layer формирует контролируемые инкременты и суточные срезы. Airflow запускает их загрузку и сверку. Kafka → Spark → Iceberg обслуживает события; архивы RB поступают в объектную landing-зону и обрабатываются Spark. Подготовленная история передаётся в DWH только через проверенную batch-загрузку, с исключением пересечения с текущими инкрементами.

Сплошные стрелки на схеме обозначают данные, пунктирные управление или метаданные. Шифрование, сервисные роли, маскирование и права BI действуют во всех контурах; PAN заменяется токеном. Документные файлы хранятся в закрытой объектной зоне, метаданные и связи в реестре документов; они не становятся автоматически таблицами Lakehouse.

Владельцы доменов отвечают за смысл и качество, Data Office за общие правила и каталог, ИТ за платформу. Регуляторный срез публикуется после финансовой сверки и утверждения; сбой аналитики не останавливает клиентские операции. Назначение Airflow соответствует его [batch-модели](https://airflow.apache.org/docs/apache-airflow/stable/index.html).
