# Аналитическая модель: исходящие платежи

Выбрана **звезда** для анализа исполненных исходящих платежей со счетов банка. [Исходник схемы Mermaid](diagrams/payment-star.mmd).

**Зерно факта:** один исполненный платёж; уникальный бизнес-ключ `(bank_id, origin_system, origin_payment_id)` сохраняется при миграции. События статусов и проводки не создают дополнительные строки этого факта. Неисполненные распоряжения в эту витрину не входят.

| Тип | Таблица | Ключ и основные данные |
|---|---|---|
| Fact | `fact_payments` | `payment_sk` PK; семь FK на измерения; исходный ключ, дата исполнения, `payment_amount` (decimal), `payment_count = 1`; `original_payment_id` для возврата при наличии |
| Dimension | `dim_customer` | `customer_sk` PK, `global_customer_id`, тип лица, сегмент, период версии; владелец счёта плательщика |
| Dimension | `dim_account` | `account_sk` PK, устойчивый ID счёта плательщика, тип счёта; чувствительный номер не публикуется |
| Dimension | `dim_product` | `product_sk` PK, ID/версия продукта счёта, название, семейство, бизнес-линия |
| Dimension | `dim_date` | `date_sk` PK, день исполнения, месяц, квартал, год |
| Dimension | `dim_currency` | `currency_sk` PK, код и название валюты суммы платежа |
| Dimension | `dim_channel` | `channel_sk` PK, код и название канала инициирования |
| Dimension | `dim_bank` | `bank_sk` PK, ID юридического лица банка, наименование |

Измерения соединяются непосредственно с фактом. Клиент и продукт историзируются по SCD Type 2: новый набор атрибутов получает новый surrogate key; факт ссылается на версию на момент исполнения. Владелец и продукт определяются по договору счёта на эту дату, а не по текущей CRM-записи. Неоднозначная роль владельца требует разбора до публикации.

Суммы агрегируются внутри одной валюты; конвертация требует отдельного согласованного курса и правила. Возврат является отдельным исполненным платежом со ссылкой на исходный, если связь доступна. Комиссия и дебетовые/кредитовые проводки не прибавляются к сумме распоряжения. Копия той же операции в Cards или RB DWH не создаёт второй платёж.

Звезда подходит для OLAP: предсказуемые соединения, фильтры по периоду/клиенту/продукту и простые агрегаты количества и суммы. Факт партиционируется по дате исполнения; уникальность исходного ключа контролируется загрузчиком между партициями. Детальные финансовые сверки используют учётное ядро DWH, а не только эту витрину.
