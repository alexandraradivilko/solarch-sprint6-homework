# Потоки данных: состояние через 3 месяца

[DFD в SVG](diagrams/dfd-3-months.svg) · [Исходник Mermaid](diagrams/dfd-3-months.mmd)

Диаграмма показывает укрупнённые потоки на границах систем, как требует уровень 0 в задании. Внутренние процессы приложений не детализированы. Общий аналитический слой размещается в FU DWH; Integration Layer использует FU ESB и адаптеры RB. Пригодность этих платформ требуется подтвердить нагрузочной проверкой.

| ID | Источник | Приёмник | Передаваемые сущности | Действия | Режим обмена | Зачем нужен поток |
|---|---|---|---|---|---|---|
| F01 | FU CRM, RB CRM | Integration Layer | Клиенты, обращения, согласия, метаданные документов; изменения разрешений/удаления | Read → Validate | Асинхронные события | Получить исходные клиентские данные и изменения обслуживания |
| F02 | FU Core, RB Core | Integration Layer | Клиентские реквизиты, счета, договоры, платежи, операции/проводки, остатки; продукты, тарифы, справочники | Read → Validate | CDC; batch контрольного среза | Получить учётные факты и данные для сверки |
| F03 | FU Cards, RB Cards | Integration Layer | Карты, держатели, договоры, статусы; продукты/тарифы и локальные ID | Read → Validate | Асинхронные события | Дополнить профиль карточными данными без повторного учёта операций Core |
| F04 | FU Loans, RB Loans | Integration Layer | Кредиты, договоры, графики; продукты/тарифы и локальные ID | Read → Validate | CDC | Получить продуктовые условия и кредитный портфель |
| F05 | Integration Layer | MDM Customer Hub | Клиентские атрибуты/ID, ограничения согласий; продукты, тарифы и справочники на согласование | Validate → Enrich → Create/Update | Асинхронные события | Сопоставить клиентов, сформировать эталон и маппинги кодов |
| F06 | MDM Customer Hub | Integration Layer | Золотые записи, общий ID и соответствия, утверждённые каталоги, разрешённые изменения/удаления | Read → Enrich | Асинхронные события | Распространить эталоны и обогатить потоки общими ключами |
| F07 | Integration Layer | FU CRM, RB CRM | Разрешённые поля общего профиля, общий ID, справочные проекции и изменения ограничений | Update / Delete | Асинхронные события | Сделать общий профиль доступным менеджерам; удалить разрешённые к удалению поля проекции |
| F08 | Integration Layer | DWH | Данные F01–F04 и эталоны F06; документы только как метаданные | Create/Update/Delete → Validate → Enrich → Aggregate | Batch каждые 15 минут; суточное закрытие | Построить общую историю и сверенные витрины клиентов, счетов, продуктов, операций |
| F09 | DWH | BI | Агрегаты и разрешённые детальные витрины | Read | Синхронный SQL | Дать аналитикам единые показатели без запросов к OLTP |
| F10 | DWH | Внешний потребитель регуляторной отчётности | Утверждённый отчётный срез | Read / Aggregate | Batch | Выпустить сверенную отчётность после приёмки финансовым департаментом |
| F11 | Integration Layer, MDM, DWH, BI | DataHub | Схемы, владельцы, классификация, lineage, результаты DQ | Create / Update | Асинхронная публикация метаданных | Проследить путь от исходной записи до показателя |

Действия слева от стрелки выполняются при чтении источника, справа в приёмнике. Integration Layer проверяет схемы, маршрутизирует и добавляет подтверждённый общий ID; MDM выполняет сопоставление; DWH сверяет финансы и агрегирует. DataHub хранит метаданные, а не копии клиентских записей.

**Delete** применяется только к полям/проекциям, удаление которых согласовано владельцем с учётом хранения. Отзыв согласия передаётся как Update ограничения; финансовые факты и история соответствий не удаляются. Изменения из MDM помечаются происхождением и не возвращаются из CRM как новые первичные изменения.

В начале выполняется согласованный снимок, затем изменения подхватываются с его позиции журнала/событий. Неразрешённые клиентские связи остаются в staging; спорные сопоставления разбирает steward. Существующие FU/RB DWH и BI продолжают локальную отчётность до приёмки общего среза; частичный FU Data Lake не участвует в обязательных потоках первого этапа.
